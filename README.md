# asmfw

A UEFI firmware written entirely in assembly. It starts at the x86 reset
vector, brings up a machine that has nothing set up on it, and hands control to
`\EFI\BOOT\BOOTX64.EFI` through a real EFI System Table.

No C, no linker, no EDK II. One NASM invocation produces the 1 MiB flash image.

```
make          # build the firmware and a test disk
make run      # boot it in QEMU, with a window
make serial   # boot it with no display, serial log only
make ovmf     # boot the same disk under real OVMF, as a control

make kernel   # build the kernel and its own disk
make runk     # boot the kernel, with a window
make serialk  # boot the kernel, serial log only

make check    # boot both disks, and both controls, and assert the log
```

## What it does

```
0xFFFFFFF0  reset vector
    |
   SEC   real mode: A20, a flat GDT, protected mode
         32-bit: identity map the low 4 GiB with 2 MiB pages, enter long mode
    |
   PEI   size RAM from CMOS, arm the page allocator
    |
   DXE   assign every PCI BAR on the machine
         set a 1024x768x32 mode and draw a text console into the framebuffer
         probe the ATA primary master
         tell the keyboard controller to translate to scan code set 1
         build the EFI System Table, Boot Services, Runtime Services
         run QEMU's ACPI loader script and publish the RSDP
         place QEMU's SMBIOS tables, patch the anchor, publish it
    |
   BDS   find the EFI system partition (GPT, or MBR type 0xEF)
         mount FAT32, walk to \EFI\BOOT\BOOTX64.EFI
         load the PE32+ image, apply base relocations
         call its entry point with (ImageHandle, SystemTable)
```

Everything the firmware prints goes to two consoles at once: COM1 at 115200,
and the framebuffer.

## Protocols published

| Protocol | Notes |
| --- | --- |
| `EFI_SIMPLE_TEXT_OUTPUT_PROTOCOL` | full, including `SetAttribute` against the standard 16-colour palette |
| `EFI_SIMPLE_TEXT_INPUT_PROTOCOL` | polled i8042, scan code set 1, arrows and Esc mapped; unshifted only |
| `EFI_GRAPHICS_OUTPUT_PROTOCOL` | one mode; `Blt` implements all four operations |
| `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL` | read-only FAT32 |
| `EFI_FILE_PROTOCOL` | `Open`, `Read`, `GetInfo`, `SetPosition`; directories enumerate |
| `EFI_BLOCK_IO_PROTOCOL` | the whole disk, read-only |
| `EFI_LOADED_IMAGE_PROTOCOL` | on the started image |

Boot Services implements memory (`AllocatePages` with all three allocation
types, `AllocatePool`, `GetMemoryMap`, `ExitBootServices`), protocol lookup
(`HandleProtocol`, `LocateProtocol`, `OpenProtocol`, `LocateHandle`,
`LocateHandleBuffer`), `InstallConfigurationTable`, `Stall`, `CopyMem`,
`SetMem`, `CalculateCrc32`, `Exit`, and the event calls ConIn needs. The rest
return `EFI_UNSUPPORTED` from a real function rather than being null pointers,
so a caller gets a status code instead of a fault.

Runtime Services implements `GetTime` off the RTC and `ResetSystem`. The
variable store reports empty, because there is none.

## The payload is the test

`payload/hello.asm` is a genuine UEFI application whose PE32+ headers are
written out by hand rather than produced by a linker — which makes it readable
as documentation for what the loader in `pe.asm` has to understand.

It matters that it is genuine: it runs under OVMF as well as under asmfw. That
makes it a control. If it works under OVMF and not here, the firmware is at
fault; if it works under neither, the payload is. `make ovmf` runs exactly that
comparison, and it caught two real bugs during development — a truncated GPT
partition array, and a path parser that restarted at the root on every
separator.

What it checks, step by step, and why each step has a wrong answer that would
otherwise look right, is in [REFERENCE §10](REFERENCE.md).

## The kernel

`kernel/` is a second thing entirely: not firmware, but something the firmware
boots. It arrives as `\EFI\BOOT\BOOTX64.EFI` on its own disk, uses boot
services for exactly as long as it takes to find the framebuffer and take the
memory it will still need, and then calls `ExitBootServices` and never speaks
to the firmware again.

What follows that call is the point of it:

```
own page tables    one address space per task: the low 4 GiB identity mapped
                   in 2 MiB pages as supervisor, plus exactly one 2 MiB page
                   carrying U/S -- that task's window, and nothing else
own GDT and TSS    kernel and user descriptors in the order SYSRET's selector
                   arithmetic demands, and RSP0 so a fault in ring 3 has a
                   stack to be reported on
own IDT            256 vectors, all of them landing in a handler
virtual wire       the local APIC's LINT0 as ExtINT, without which the 8259
                   is programmed correctly and connected to nothing
8254 at 100 Hz     the tick that takes the CPU away from a task
i8042 on IRQ1      translation on, break codes seen, keys queued
SYSCALL/SYSRET     EFER.SCE, STAR, LSTAR, FMASK
own disk stack     ATA PIO, GPT, FAT32 -- the firmware's went away with it
iretq              into four tasks that run at CPL 3, round robin
```

System calls run with interrupts on, so a task can be preempted inside one.
What keeps two writers from interleaving is a lock, not a masked timer: the
second one blocks, and blocking means the CPU goes to somebody else rather
than round a spin loop. `sys_sleep` blocks the same way, against the tick
instead of against a lock, and when nothing is runnable at all the kernel
parks on `hlt` until a tick makes something runnable again.

A task that gives up the CPU inside a system call presents a problem: its
state is spread across a stack frame the switch cannot resume, because the
switch understands interrupt frames and nothing else. So the kernel raises an
interrupt against itself — `int 0x81`, on a gate ring 3 cannot reach — which
turns the one into the other. One save format, one way back in.

A task's registers live on its own kernel stack, so a switch is one store of
RSP and one load of the next task's; the task structure holds no register
file. What that buys is that a task which has never run and a task which was
interrupted mid-instruction are the same shape, and one code path starts both
— `task_create` simply writes down the frame the interrupt would have left.

The four tasks are four separate programs, read off the disk by the kernel
after the firmware is gone, and they end four different ways.

A program is a flat binary: no headers, no relocations, an entry point at
offset zero. The kernel reads it straight into the window it will run in and
starts it, so every reference in it has to be RIP-relative, and everything it
knows about the machine it is told at entry — `RDI` is its task id, `RSI` its
window, `RDX` its neighbour's. That is the whole loader.

**Task 0** (`\PROGS\MAZE.BIN`) generates a 39x19 maze by randomised depth-first search, solves it,
and draws it. It never yields, so every time it disappears for a while it is
because the timer took it away mid-instruction and put it back later without
its noticing. It ends by calling `sys_exit`.

**Task 1** (`\PROGS\COUNT.BIN`) prints a numbered line and then sleeps 120 ms,
eight times over. The uptime beside each line is the visible part: the steady
twelve-tick gaps are the sleep, and the one long gap is task 0 holding the
console while it draws its maze. It ends by executing `cli`, and is killed by
the `#GP` that follows.

**Task 2** (`\PROGS\ROGUE.BIN`) goes looking for memory that is not its own. First it hands the
kernel a pointer outside its window and is refused — `sys_write` checks the
bounds once, at the boundary, and the loop behind it trusts that check. Then
it reads task 0's window directly, at an address the kernel told it, with no
system call involved. That address really is mapped, and the kernel can read
it; in task 2's own address space that 2 MiB page has no user mapping, so the
read faults with `#PF` error 5 and the task is gone.

**Task 3** (`\PROGS\TYPE.BIN`) calls `sys_read` and waits for a keystroke, which
is the one thing on this machine no clock will eventually produce. The other
three would run identically with nobody at the keyboard; this one is the
reason the kernel's idle path had to become honest. Every other block ends at
a tick that can be named in advance — a sleeper's deadline, a lock's release
— so `hlt` was always a wait for arithmetic that had already been done. A task
blocked on the keyboard can leave the machine genuinely idle with work
outstanding, for as long as nobody types. It echoes what arrives, with the
uptime beside it, and gives up after three seconds of silence, which is what
happens under `make serialk`: with no display, QEMU has no keyboard to give
it. Enter ends it either way.

None of the four takes the machine with it. That is what the arrangement
exists to demonstrate.

The kernel runs under OVMF too, at a completely different load address, and
does the same thing there — which is the same control the payload provides,
applied to something considerably easier to get subtly wrong.

## Limitations, stated plainly

- **QEMU only.** The firmware assumes RAM works at reset. On real hardware it
  does not: the memory controller has to be trained first, and on any Intel
  platform after Ivy Bridge that code exists only as Intel's closed FSP binary.
  This is why coreboot exists and why coreboot still ships a blob. Getting this
  onto a real board means becoming a coreboot payload, not flashing it.
- **Nothing is ever freed.** `AllocatePages` is a bump pointer; `FreePages` and
  `FreePool` succeed and do nothing. The firmware allocates a handful of times
  and then hands the machine over.
- **ACPI and SMBIOS come from QEMU, as built.** The ACPI tables QEMU describes
  through `fw_cfg` are placed and the RSDP goes into the configuration table
  under both the ACPI 1.0 and 2.0 GUIDs. The SMBIOS tables are placed as QEMU
  built them, the anchor gets its address and checksums, and it is published
  under the SMBIOS or SMBIOS3 GUID to match its signature. No structure is
  added: OVMF supplies a type 0 when QEMU does not, and this firmware does not,
  so it publishes one fewer. The ACPI loader script's `WRITE_POINTER` command is skipped as well: it writes
  back into `fw_cfg`, which only matters to features this firmware does not
  expose.
- **No `SetVirtualAddressMap`.** Runtime services stay valid only at their
  physical addresses.
- **FAT32 short names only.** Long-name entries are skipped, not decoded.
- **No `LoadImage` / `StartImage`.** BDS loads the one image it boots; a loader
  cannot ask the firmware to load another.
- **One ATA disk**, primary master, PIO, LBA28.
- **No Secure Boot**, no variable store, no setup UI.
- **Round robin, and no priorities.** The next runnable task after the current
  one wins, and that is the whole policy. A task blocked on a lock, a deadline
  or a keystroke is skipped; nothing is ever preferred to anything else, and a
  task that wakes waits its turn like any other.
- **Only the first byte of a syscall is uninterruptible.** `FMASK` clears `IF`,
  and the kernel sets it again as soon as the stack is its own, so the rest of
  a system call is preemptible. What keeps two writers from interleaving is the
  console lock, not a masked timer.
- **A keystroke is delivered on the next tick, not immediately.** The keyboard
  interrupt queues the byte and makes the waiter runnable, and then returns to
  whoever was running; it does not switch. So a key can wait up to 10 ms for
  the task that wanted it to be scheduled. That is invisible to a typist and
  would not be to anything faster.
- **The keyboard is one board with no modifiers but shift.** Caps lock, ctrl
  and alt produce nothing, extended keys — the arrows, the keys duplicated on
  the right — are consumed and dropped, and there is no key-up event: the ABI
  carries bytes. The queue is 32 bytes and drops what does not fit.
- **The firmware's `ConIn` cannot see shift at all.** It polls, so it never
  sees a break code, so it cannot know whether a modifier is still held. It
  reports the unshifted character. The kernel's driver is interrupt-driven and
  does track shift, which is the whole difference between the two.
- **The kernel's storage stack is the minimum that boots it.** Primary master
  only, polled PIO, LBA28, read only; GPT only, no MBR fallback; FAT32 with
  short names only. This is why `make ovmfk` uses the i440fx machine and not
  q35 — the kernel drives the legacy ATA ports itself, and q35's disk is
  behind AHCI.
- **The kernel's console is text only.** `sys_write` is the whole output path,
  so the maze is drawn in characters. Ring 3 cannot reach the framebuffer:
  it is outside the user window, which is the point.
- **The kernel never returns to the firmware.** Which is correct — after
  `ExitBootServices` there is nothing to return to. When the last task has
  ended it halts, and when every task is merely blocked it idles on `hlt`
  until an interrupt makes one of them runnable again.

## How it is checked

There is no test framework here, and there cannot be one in the usual sense:
the unit under test is a machine at reset, and the only thing in a position to
observe it is the code being tested. What stands in for one is the serial
transcript.

`make check` boots both disks under a timeout — nothing here exits QEMU, both
images halt on purpose — and asserts that the transcript still contains the
landmarks it contained before: every phase marker in order, the payload's ACPI
checksums and what `ConIn` returned, the kernel's bring-up lines, and all four
task endings, including the two that are deaths. One assertion is negative:
`cs 0008` in a trap frame is a trap taken in ring 0, and if it appears the
kernel itself has gone wrong. Then it runs the same two disks under OVMF,
which is the only comparison that can tell a firmware bug from a payload bug.

```
make check          both disks, then both controls
make check-fw       the firmware and the payload it boots
make check-kernel   the kernel only
make check-docs     the module docs' line numbers, which `check` runs first
```

The assertions are in [tools/smoke.sh](tools/smoke.sh), transcripts land in
`build/logs/`, and a skipped OVMF control is not a passed one.

## Notes on the parts that were not obvious

**The reset vector must jump *near*.** At reset `CS.base` is `0xFFFF0000` with
`CS` reading `0xF000` — a hidden state no far jump can reproduce. A far jump
would reload `CS` and recompute the base as `0xF000 << 4`, landing in the low
megabyte where nothing has been mapped. So the first instruction is a near
jump, and every byte it can reach lives in the last 64 KiB of the volume.

**Nothing on the machine has an address.** QEMU hands the firmware a board
whose PCI BARs all read back zero. Assigning them is firmware's job and nobody
else's, which is why the framebuffer did not exist until `pci_assign_resources`
was written.

**A VBE mode is not enough to get a picture.** The attribute controller's
palette-address-source bit still gates the display, and the chip comes out of
reset with it clear. On a normal PC the video option ROM sets it during INT 10h
mode setting. There is no option ROM here, so `vga_unblank` does it.

**The keyboard does not send the codes every table is written against.** A
PS/2 keyboard's own default is scan code set 2. What every operating system
decodes is set 1, and what turns one into the other is a translation bit in
the i8042's command byte that comes out of reset clear — on a normal PC the
BIOS sets it during keyboard bring-up. This is the same shape as the VBE
palette-address-source bit above, with one difference that made it worse: a
display with that bit clear shows nothing, and is therefore obviously broken.
A set 1 table reading set 2 codes does not fail. It decodes them into other
keys, and answers every call with a plausible wrong letter — `h` came back as
`,` twice, because the `0xF0` that introduces a set 2 release looks like a key
this table does not know and the code behind it then reads as a fresh press.

**A protocol nothing exercises is a protocol nobody has tested.** The firmware
published `EFI_SIMPLE_TEXT_INPUT_PROTOCOL` for the whole of its existence with
that bit unset, and it was the kernel's driver that found it, because no
payload here had ever read a key. `payload/hello.asm` now polls `ConIn` for
the three seconds it used to spend stalling, and prints what it got. Under
OVMF and under asmfw it prints the same letter, which is the comparison that
makes it worth running at all.

**ACPI tables arrive unfinished.** QEMU does not hand over tables, it hands
over blobs plus `etc/table-loader` — a script of allocate, add-pointer and
add-checksum commands. Every cross-reference inside those blobs is an offset
until firmware turns it into an address, and every checksum is wrong until
firmware redoes it afterwards. Downloading the blobs and publishing the RSDP
without running the script yields tables that look plausible and point at
nothing, which is why `payload/hello.asm` walks the XSDT and sums each table
rather than merely reporting that one exists.

**A kernel cannot inherit a driver.** The firmware has an ATA driver, a GPT
parser and a FAT32 reader, and the kernel reimplements all three, because
`ExitBootServices` is exactly the moment those stop existing. Nothing in this
project makes the point more plainly: the two readers sit in the same tree,
solve the same problem, and cannot share a line of code.

**A correctly programmed 8259 can be connected to nothing.** The kernel's
timer did not fire, and every obvious cause checked out: the PIC was remapped,
IRQ0 unmasked, the 8254 loaded, `IF` set in the faulting task's saved flags.
The missing piece was the local APIC. QEMU only delivers a PIC interrupt to
the CPU when the APIC is hardware-disabled or has `LINT0` unmasked, and out of
reset every LVT entry is masked. On a normal PC the BIOS programs `LINT0` as
ExtINT — virtual wire mode — and asmfw does not, because nothing had ever
needed an interrupt before. The kernel does it for itself now, and checks the
tick arrives before anything depends on it: a scheduler whose timer never
fires looks exactly like one that works and is simply never asked to switch.

**`default rel` is not a style choice.** The volume is assembled at
`0xFFF00000`. A 64-bit absolute `disp32` sign-extends, so `[label]` would
address `0xFFFFFFFFFFF00000`. Every 64-bit reference is RIP-relative; the ones
that genuinely are low absolute addresses are written `[abs ...]`.
